# GPT 直充交付 + 资金护栏 · 设计

## 目标
- 兑换策略增加「GPT 交付方式」：**卡台 CDK**（现状）或 **直充**。两种并存，按策略逐步切换。
- 直充使用卡台的「自动选卡直充」接口（`POST /gpt-direct/auto-orders`）：选卡、注资、换卡重试都由卡台完成。
- 直充上线前先有自己的资金护栏：单笔上限、每日总额熔断、连续失败熔断、钱包余额告警，告警走现有的 Telegram 通知。
- X / TG 不变，继续走卡台 CDK。

## 范围和约束
- 只有**自有码**策略可以选直充。托管码本身就是卡台 CDK，不能直充。
- 直充只支持 `go / plus / pro_5x / pro_20x`（自动直充接口的 `plan` 枚举里没有 `pro_25x` 和 Credits）。在直充策略下生成 `pro_25x` 批次会被拒绝。
- **Credits 不在这一期**：只有需要我们自己指定卡的普通直充下单接口支持它，和「选卡交给卡台」的目标冲突，以后单独做。
- 交付方式、结账地区在**生成批次时快照**进 `batches.params`（和「每码独立支付」一样属于「生成时写入」）。改策略只影响之后生成的码，已经发出去的码行为不变，可以预期、也方便核对成本。
- 结账地区也用于卡台 CDK 模式：卡台目录返回 `cdkRegionSelectionEnabled = true` 时，生成 GPT 卡台码会带上 `paymentCountry`（兑现上一份 API 变更分析的结论）。

## 兑换流程（直充）

| 步骤 | 卡台 CDK（现状） | 直充 |
|---|---|---|
| ① 输码 | 生成 / 复用卡台码，调用公开接口 preview | 只在本地检查，不调用卡台 |
| ② 贴 Session | 公开接口 preflight | `POST /gpt-direct/preflight`（带策略的结账地区），拿到账号、当前套餐、地区和币种、`quoteEstimatesUsd` |
| 账号规则、价格保护 | 照旧 | 照旧。当前成本 = 美元报价估算 + 服务费，和批次成本快照比较 |
| ③ 确认 | 公开接口 redeem | **先过资金护栏**，再 `POST /gpt-direct/auto-orders` |
| ④ 进度 | 公开接口 result + Webhook | `GET /gpt-direct/auto-orders/{id}` + Webhook（`openai.direct.*` 按 orderId 触发刷新） |
| 需补交 Session | `/gpt-direct/orders/{id}/session` | 同一个接口，orderId 取自动直充任务里最新一次尝试的订单 |

自动直充请求体：
- `credential`：用户的 Session（只在内存里保留 30 分钟，照旧不落库）
- `plan`
- `paymentCountry / paymentCurrency`：用预检返回的值
- `expectedAmountUsd`：预检的 `quoteEstimatesUsd[plan]`
- `expectedCustomerServiceFee / pricingVersion`：取套餐目录
- `maxTotalDebitUsd`：护栏的单笔上限。卡台会按这个预算封顶，等于多了一道卡台侧的保险
- `forceNewCard`：取策略里的「每码独立支付」
- `productCode`：取「设置 → 付款通道」

**幂等**：键为 `ao-{兑换ID}-{第几次}`，写在 `redemptions.client_request_id`。超时或 5xx 时结果未知，进入轮询，用**同一个键和同一个请求体重放**（接口要求「先查询或用原幂等键重放，禁止换键重下」）。重放需要 Session，Session 已经过期就转人工核对，绝不换键重下。

**失败**：卡台自动直充内部已经会换卡重试（最多 2 张卡），所以直充模式下我们**不再叠加自动重试**，避免重复付开卡费。策略的「自动重试」在直充模式下按「释放码」处理；选了「转人工」的仍转人工。后台可以手动重试，手动重试同样要过护栏。

**状态映射**（自动直充任务 → 兑换状态）

| 任务状态 | 兑换状态 |
|---|---|
| queued / running / pending | processing（阶段显示尝试状态：注资 / 付款 / 待确认） |
| requires_action | 查最新一次尝试的订单。`nextAction = submit_session` 就让用户补交 Session，否则转「需处理」提醒卖家 |
| completed | completed，成本取实际扣款 |
| failed | 按策略释放码或转人工 |

## 资金护栏

新增设置 `directGuard`：

| 项 | 默认 | 作用 |
|---|---|---|
| 每单预算 `bufferPct` / `feeBufferUsd` | 15% / $2 | 每单预算 = 预估成本 ×(1 + 15%) + $2（给开卡 / 换卡费用留余量）。它既是这一单在每日额度里的预留额，也作为 `maxTotalDebitUsd` 发给卡台，由卡台再封顶一次。按每一单算，Go 不会拿到 Pro 级别的扣款上限 |
| `perOrderMaxUsd` 单笔硬上限 | 250 | 每单预算超过它就转人工，不下单（默认能放行 Pro 20x） |
| `dailyMaxUsd` 每日总额 | 1000 | 按业务时区计算当天已占用，加上这一单的预算超过上限就转人工，并立即推送告警（每天一次） |
| `maxPerCode` 每张码直充次数 | 3 | 直充失败后码会释放、买家可以重兑，每次都有开卡费；同一张码累计直充（卡台没受理的不算）达到上限就转人工 |
| `failTrip` / `tripAccounts` 自动熔断 | 5 笔 / 3 个账号 | 最近 N 笔已结束的直充**都失败**，**并且涉及至少 K 个不同账号**，才自动暂停全部直充并告警。只看笔数的话，一个人反复故意失败就能让全站停摆 |
| `lowBalanceUsd` 余额告警 | 100 | 卡台钱包可用余额低于它时推送告警（6 小时内一次）；只在有策略使用直充时检查 |
| `paused` 暂停开关 | 否 | 手动暂停 / 恢复；自动熔断也会打开它，必须人工恢复 |

**额度账本** `direct_spend` 表：每次下单前，在同一个事务里检查护栏，并写一条 `reserved`（预留额 = 这一单的预算）。
- 成功：改为 `spent`；失败：改为 `released`。两种情况都按**所有尝试**（包括失败那张卡）订单费用明细里已扣款的美元项算实际花费（订阅款 + 服务费 + 开卡费 + 充值费；转到卡上的本金不算）。订阅款不是美元时用预检的美元估算代替，并在备注里注明。
- 费用明细里还有 held / pending / unknown，或者明细拿不到：先按已知金额记、标记「待核对」（`cost_verified = 0`），期间按预算计入额度；后台每 5 分钟对账，补齐后改为已核对，并回填兑换成本和自动续费状态。超过 7 天还核对不了的不再自动跟进，护栏面板显示数量。
- 结果未知（网络中断、超时、5xx、响应体读不完或解析不了、成功响应却没有任务 ID、本地异常）：保持 `reserved`，用原幂等键原样重放。已经拿到任务 ID 的，之后只查这个任务，本地处理出错也不会回到「重新下单」。Session 已过期、无法重放的，转「需卖家处理」。
- 卡台明确拒绝下单（4xx，带错误码）：改为 `cancelled`，不计入额度。其中余额不足会转人工并立即告警。

**人工核对**：卖家到卡台查清结果后，在兑换详情里登记——「已开通 / 没开通」和「实际花费」分开填（开卡费扣了但会员没开通很常见，不能用金额推断结果），或者填找到的卡台任务 ID 让系统接着自动查。兑换状态、兑换码、额度账本在同一个事务里一起更新，必须写核对依据，并记审计日志。

**结果没出来时的限制**：只要这张码还有 `reserved` 的直充，就不能释放、拒绝、撤销，所在的商城订单也不能退款（强制也不行）——钱可能已经付出去了，这些操作会让同一张码再付一次钱。

**账号名额**：预检不占名额（同一账号可以用几张码各自完成预检），确认付款时复查并立即进入「处理中」，两步之间没有 await，单进程内并发确认不会同时通过。卡台 CDK 流程同样适用。

当天占用 = 今天创建、已结束的直充（已核对按实际花费，待核对按预算和已知花费的较大值）+ **所有还没结束的预留（不管哪天创建）**。跨过零点仍在付款的单不会从额度里消失。因为检查和写预留在同一个同步事务里，并发确认也不会一起冲破上限。

被护栏拦下的兑换进入「待审核」（阶段 `guard`），**码不消耗**；买家页面显示「已提交，等待卖家确认」。卖家调整护栏或恢复直充后点「继续开通」，系统会重新预检再下单；如果仍被拦下，接口会返回原因，后台直接提示，不会显示成功。Session 过期就提示用户重新粘贴。

**需要卖家处理**（任务 `requires_action`、但不是要补交 Session）：买家页面不会提示补交 Session，系统每 5 分钟慢速查询一次任务（Webhook 到达时也会立即刷新），卖家在卡台处理好后自动跟上。

**通知**：熔断、当日额度用完、钱包余额低、余额不足被拒——这些资金告警只要配置了 Telegram 机器人就**总是发送**，不受「兑换需要关注」开关控制。被拦下的兑换本身也会出现在每分钟的「需要关注」汇总里（跟随开关）。

**其他细节**
- 自动取消续费由卡台 API Key 的设置决定（默认开启）。直充完成页以订单返回的 `willRenew` 为准；仍开启时提示买家自己去关闭。
- 买家看到的进度和提示不出现「付款」、不出现错误码（例如「开通尝试 1 · 未成功」「这次没有开通成功」），错误码只在后台显示。
- 批次成本快照记录口径 `costBasis`。目录不是美元、退回用 CDK 售价时，兑换时不做价格保护，避免拿两种口径互相比较。
- 卡台目录缓存 5 分钟。卡台关闭「生成 CDK 时选地区」后，最多 5 分钟内生成带地区的卡台码会被拒（商城发货会自动重试并恢复）；后台「售价与利润」页的刷新按钮可以立即清缓存。
- 商品和策略的组合要校验：直充策略不能绑定直充不支持的套餐；已经绑着这类商品的策略不能改成直充。否则买家付款后会一直发不出货。

## 上线前要用真实卡台核对
1. 用 Go 套餐真实直充一单：核对 `quoteEstimatesUsd`、费用明细 `financials`、`willRenew` 的字段名和取值，以及记录的成本是否准确。
2. 失败时 `reservedDebitUsd` 的确切含义。
3. 需要补交 Session 的流程：`nextAction = submit_session` → 补交后任务能否继续。
4. API Key 权限：GPT 直充写权限、自动开卡权限，以及自动取消续费的设置。

## 测试（模拟卡台 + `scripts/e2e-direct.ts`，纳入 `npm test`）
1. 直充策略生成批次；`pro_25x` 被拒绝；批次快照了 `delivery` 和地区
2. 正常兑换 → completed，没有生成卡台码，额度账本为 `spent`
3. 拒付 → 失败释放码，不叠加自动重试
4. 需要补交 Session → 补交后完成
5. 第一次下单返回 5xx（实际已受理）→ 用原幂等键重放，卡台侧只有一个任务
6. 单笔上限低于报价 → 待审核，没有向卡台下单
7. 每日总额用完 → 待审核 + Telegram 告警
8. 连续失败熔断 → 自动暂停 + 告警；恢复后后台「通过」→ 完成
9. 钱包余额低 → 告警
10. 原有卡台 CDK 流程（GPT / X / TG）全部测试照旧通过
