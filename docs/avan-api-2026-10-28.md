# 卡台 API 文档变更分析：2026-09-30 → 2026-10-28

对比 `avanfinity-openapi (4).json` 和 `(5).json`。接口路径没有增删，只改了 GPT 相关的 9 个 schema 和 `POST /gpt-direct/cdks/generate` 的说明。X / TG 部分、公开兑换接口 `/api/public/cdk/*` 都没有变化。

## 一、变更清单

| # | 变化 | 位置 | 对我们的影响 |
|---|---|---|---|
| 1 | **CDK 绑定结账地区**：生成时可以传 `paymentCountry`（如 `US`、`PH`），生成后地区和币种就固定下来；不传就固定为**生成那一刻**的默认地区。返回结果新增 `checkoutRegion { country, currency }` | `CdkGenerateInput` / `CdkGenerateResult` / 新增 `CheckoutRegion` | **大**，见第二节 |
| 2 | 套餐目录新增 `checkoutCountries`（可选地区和对应币种）、`batchConcurrencyByCountry`（各地区批量并发能力的快照）、`cdkRegionSelectionEnabled`（是否支持生成时选地区） | `GptPlansResponse`（这三个字段是 required） | 中：要读取并展示 |
| 3 | **兼容兜底**：只有 `cdkRegionSelectionEnabled === true` 时才发送 `paymentCountry`；为 false 或旧版卡台没有这个字段时不发送。不传地区时会兜底到默认地区 | `cdkRegionSelectionEnabled` 字段说明 | 我们必须照这个规则做，否则旧卡台会因为 `additionalProperties: false` 拒绝请求 |
| 4 | 改变地区必须换一个新的幂等键 | generate 接口说明 | 小：我们的幂等键是每次请求唯一的，但要把地区写进批次参数 |
| 5 | 新增 Credits 套餐：目录里出现 `credits_250/1000/2500/5000`，直充下单的 `plan` 允许 `credits_N`（N 为 250–9999999） | `GptPlan.key`、`GptCreateOrderInput.plan` | 中：`catalog.ts` 里套餐 key 是写死的，新套餐不会显示，也不能卖。注意 CDK 生成接口的 `plan` 枚举**没有**加 credits，所以 credits 暂时只能直充、不能做成 CDK |
| 6 | 凭证新增 `password` 模式（邮箱 + 密码 + TOTP 密钥）；`access_token` 模式标记为弃用，直充会返回 `GPT_ACCESS_TOKEN_UNSUPPORTED`，要求使用同时包含 sessionToken 和 accessToken 的完整 Session JSON | `GptCredential` / `GptPasswordCredential` | 小：我们只用 `session` 模式。但兑换页 `parseGptSession` 目前只要求有 accessToken / sessionToken / user 其中之一，应该收紧，提前拦截不完整的 Session |
| 7 | 付款证据来源新增 `upstream_order` | `GptPayment.evidenceSource` | 很小：`normalize.ts` 不枚举这个字段，不受影响 |
| 8 | `info.description` 的差异全是一段混进文档的前端源码（TSX） | `info.description` | 无关。这是卡台导出文档时的问题，可以提醒对方 |

## 二、「CDK 绑定地区」对现有流程的影响

关键在于我们有两种码，生成卡台 CDK 的时机不一样：

- **托管码**：生成批次时就向卡台生成 CDK，地区当场固定。只要在批次上选地区并传过去就行。
- **自有码（推荐模式）**：买家**兑换时**才临时向卡台生成 CDK（`redeem.ts` 的 `upstreamCodeFor`），失败重试还会再生成一张新的。如果不传地区：
  1. 同一个批次的码，会按**各自兑换那天**的默认地区生成。卡台哪天调了默认地区，同一批码的结账币种和价格就会变。
  2. 批次的成本快照 `batches.cost_usd` 和策略里的「价格保护」是按生成批次时的报价算的，地区变了以后这个比较就失真了。
  3. 自动重试换卡台码时，可能换到另一个地区。

  **结论：地区必须在生成我方批次时就选定，写进 `batches.params`。之后为这个批次临时生成的每一张卡台码都带上同一个 `paymentCountry`。** 这样地区和我方批次是一一对应的。

另外：
- 卡台不支持选地区时（`cdkRegionSelectionEnabled` 为 false），批次照常生成，记录 `checkoutRegion` 为空，行为和现在一样。
- 卡台返回的 `checkoutRegion` 要存下来，和我们请求的地区核对；对不上就记日志，并把这张卡台码标记为 failed。
- `batchConcurrencyByCountry` 只是容量快照。生成页面可以用它提示「该地区当前并发低」，不建议拿来做硬性拦截。

## 三、建议的改动（还没动代码）

1. `server/avan/client.ts`：
   - `gptGenerate` 增加可选参数 `paymentCountry`，返回值类型增加 `checkoutRegion`。
   - `gptPlans` 的类型增加 `checkoutCountries`、`batchConcurrencyByCountry`、`cdkRegionSelectionEnabled`。
2. `server/services/batches.ts`：
   - 生成 GPT 批次时接收 `paymentCountry`，并校验它在 `checkoutCountries` 里。
   - 只有 `cdkRegionSelectionEnabled` 为 true 时才发送这个参数。
   - 地区写进 `params.paymentCountry`；托管码还要保存返回的 `checkoutRegion`。
3. `server/services/redeem.ts`：自有码在 `upstreamCodeFor` 里，从批次参数读出地区再传给卡台。
4. 后台页面：
   - 生成页（`web/admin/generate.html`）增加地区下拉框，卡台不支持时隐藏。
   - CDK 列表和批次详情显示地区和币种。
   - 商城商品可以选择按哪个地区发货（发货复用 `generateBatch`，所以要把地区放进商品配置，并在下单时快照）。
5. `server/services/catalog.ts`：套餐 key 和名称改成以卡台目录为准，写死的列表只作为兜底；credits 套餐先只展示，不允许生成 CDK。
6. `parseGptSession`：要求 Session 里同时有 `sessionToken` 和 `accessToken`，否则提示用户重新复制完整内容。
7. `server/mock/avan-mock.ts` 和 e2e 测试：
   - 模拟目录返回新字段，用一个开关模拟卡台是否支持选地区。
   - 测试覆盖三种情况：传了地区、旧卡台不传地区、自有码重试时地区保持不变。

## 四、需要向卡台确认的问题

1. 一张已经生成的 CDK，如果买家的 ChatGPT 账号所在地区和 CDK 的地区不一致，会怎样：拒绝、在预检阶段报错，还是照常付款？这决定了兑换页要不要提示用户选择或匹配地区。
2. 「默认地区」会不会变？多久变一次？自有码模式下是否建议总是显式传地区（我们倾向于总是传）。
3. 同一个套餐在不同地区的报价差多少？`/gpt-direct/cdk-offers` 的 `salePrice` 会不会按地区分开返回？目前 offers 接口没有地区维度，我们的成本和利润统计也没法按地区区分。
4. 「协议加了兜底」具体是指什么？文档里能对应上的只有两处：
   - 不传 `paymentCountry` 时固定到默认地区；
   - `cdkRegionSelectionEnabled` 缺失时不发送地区（向后兼容）。

   如果还有别的兜底（比如地区不可用时自动换到别的地区），文档里没有写，需要对方说明。因为自动换地区会让币种和成本变化，我们需要知道。
